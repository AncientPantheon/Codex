So the design's open questions are answerable **with evidence and with zero

#### (1) Collect does NOT touch the staked balance. Design §1's open question, closed.

`0_Stoa/coin-contract/coin-live.pact:1467-1488` is `C_URV|Collect`. Its whole
body is:

```
(C_Transmit URV|KONTO account available-rewards)   ;; :1475
(XI_URV|ResetPendingRewards account)               ;; :1477
(XI_URV|UpdateUnclaimedCount false)                ;; :1479
(XI_URV|UpdateUserRPS account (UR_URV|VaultRPS))   ;; :1481
(XI_URV|UpdateVaultSupply available-rewards false) ;; :1483
```

It never calls `XI_URV|UpdateUserScore` (`:1609-1625`), which is the ONLY writer
of the `user-supply` field that `UR_URV|UserSupply` (`:1300-1307`) reads — and
that function is called from exactly two places, `C_URV|Stake:1426` and
`C_URV|Unstake:1454`.

**So the staked figure the snapshot reads before the transaction is still
correct when Unstake runs in the same transaction.** Acceptance criterion 2 is
satisfied by that evidence, and the amount derivation needs no change.

#### (2) Collect pays out NATIVE STOA, not urSTOA — so C must run BEFORE B.

The same body: `C_Transmit` (`coin-live.pact:593-598`) is `debit` + `credit` on
the **coin-table** — native STOA. The urSTOA ledger's mover is `X_UR|Transfer`,
which is what `C_URV|Stake:1415` and `C_URV|Unstake:1449` use.

So the rewards Collect releases land in the OLD key's **chain-0 native STOA
balance**. The design says *"Collect runs FIRST so rewards land in the liquid
balance before the unstake; step D then moves the whole thing"* — D is wrong.
D moves urSTOA (`planMigrationChain` gates it on `oldKeyUrStoaLiquid`). The step
that moves native STOA off chain 0 is **B**.

And today **B is planned before C** (`migrationChain.ts:356-378`), so a press
that collects leaves that STOA sitting on a key the account stops naming at F.
The engine re-reads and re-plans after every confirmation, but it walks its
toast rows ONCE (`engine.ts:755`), so B's row is already spent by the time C
produces the balance. No money is lost — the chain is idempotent and the next
press drains it — but "one press, uninterrupted" stops being true for exactly
the account the design is about.

**Decision: the planner emits C before B.** `A(n) → C → B → D → E → F → G`.

Why that is in scope, and safe:

- The design's "Out of scope: any change to the A/B/D/E/F steps" is about what
  those steps DO. None of their pact code, amounts, signers or predicates
  change. Only C's position moves, and moving it is the direct consequence of
  design §1's own instruction to get C's interaction with the balances right
  *"against the contract's behaviour; do not guess"*.
- All three invariants `codex-core/tests/migration-chain.test.ts` pins as
  properties survive: **G is last** (`:159-166`), **the whole drain precedes F**
  (`:175-192`), **A(n) all precede B** (`:194-204`). So does **C → D → E**
  (`:206-218`).
- B's own job gets strictly better: after C it drains the collected rewards too.

The deliberate test rewrites this forces are listed under T3.

#### (3) The Ouronet gas station CANNOT pay for `define-keyset`. And it CAN pay for Collect+Unstake.

`DALOS.GAS_PAYER` (`1_SOVEREIGN/STAGE_01/2_Core/01_DALOS.pact:425-530`,
relative to the Pact tree above) inspects the transaction's
own top-level forms (chainweb supplies them to the capability as
`(read-msg "exec-code")` — see `REPL/RedTeam/[RT-I]_GasStation.repl:20-48`,
which drives the capability with `env-data { "exec-code": [...] }`) and accepts
EXACTLY three shapes (`:456-526`):

| case | lines | shape |
|---|---|---|
| 1 | `:470-485` | ONE form, starting `(coin.C_`, `(ouronet-ns.TS`, `(ouronet-ns.DSP` or `(ouronet-ns.STOAICO.` |
| 2 | `:487-496` | exactly TWO forms, **both** starting `(coin.C_` — the comment at `:486` names the example "CreateAccount + Collect" |
| 3 | `:514-524` | THREE+ forms: `(namespace "ouronet-ns")`, then `(TS01-C1.DPTF|C_Transmute…` (a ≥25-IGNIS donation), then `(let…` |

Two consequences, both load-bearing:

- **Step C's merge is blessed by Case 2.** `(coin.C_URV|Collect …)` +
  `(coin.C_URV|Unstake …)` is two `(coin.C_` forms, gas-station-sponsored,
  exactly as design §1 asks. **But three forms is not a case at all**, so
  `executeCollectUrStoa`'s `(coin.C_CreateAccount …)` prelude
  (`urStoaFunctions.js:443`) can NEVER be bundled with both. See T4 for what
  happens when the old payment address has no coin account.
- **`(define-keyset "<ns>.<ksn>" (read-keyset "ks"))` matches none of the three
  cases.** The design records *"Gas — settled by the owner: gas-station
  sponsorship applies."* Against this contract that is false. The routes are:
  (a) **self-paid gas** — an ordinary transaction whose `senderAccount` is a
  real STOA account; or (b) Case 3, which costs the patron a ≥25-IGNIS
  `C_Transmute` donation and requires the define-keyset to sit inside a `(let …)`.
  **T4 takes (a)**, and names (b) in its header as the owner's fallback if the
  IGNIS cost is preferred to spending STOA on gas.

#### (3b) …and a keyset in `ouronet-ns` cannot be redefined by a user at all

`0_Stoa/genesis/stoa-genesis-1.pact:111` is
`(define-namespace "ouronet-ns" (keyset-ref-guard "ns-operate-keyset") (keyset-ref-guard "ns-operate-keyset"))`.
The first argument is the namespace's USER guard, and `ns-operate-keyset`
(`:10`, `:118`) is a protocol keyset. `stoa-ns` (`:110`) is the same.
`free` and `user` (`:112-113`) are `GUARD_SUCCESS` — open to anyone.

So whether `define-keyset` can run at all depends on the NAMESPACE the
referenced keyset lives in, and `resolveGuardKeys.ts:76`'s own worked example of
a real account guard is `"ouronet-ns.dh_ah-keyset"`.

This plan does **not** model namespace authority in the planner — that would
need a new chain read and an allowlist, and both would be guesses. Instead:

- the planner decides executability on the one fact it can read for free:
  **is the account's guard a keyset-ref at all** (criterion 4);
- the T4 builder **simulates before it signs** (`dirtyRead` → refuse), so a
  closed namespace costs a read and never a signature;
- and the engine treats a `define-keyset` failure as **reported, never a halt**
  (T3), because nothing in A-G depends on it and halting there would block G.
  That one rule covers the closed namespace, an unsatisfiable current keyset
  that slipped past the gate, and any chain-side surprise.
- T5's gate shows a non-blocking warning when the ref's namespace is
  `ouronet-ns` or `stoa-ns`, citing `stoa-genesis-1.pact:110-113`, so the owner
  learns it before pressing rather than from a failed row.

**T4 must REPL-verify, with `~/.local/bin/pact`, which of these two shapes Pact
accepts** before building either:

```
(a) (define-keyset "free.my-keyset" (read-keyset "ks"))
(b) (namespace "free")
    (define-keyset "my-keyset" (read-keyset "ks"))
```

Shape (b) is two forms, neither of them `(coin.C_`, which independently rules
out gas-station sponsorship and so reinforces decision (3)(a).

### Where "forfeit" lives

Design §3 makes the manual-key path a PRECONDITION resolved before the first
transaction, and §3's point 2 makes forfeit one of two offered resolutions.
`checkMigrationPreconditions` (`migrationChain.ts:496-553`) is where a refusal
is produced, and the engine checks it once and returns `status: "refused"`
(`engine.ts:320-325`).

**Forfeit is carried on `MigrationChainIntent`, not persisted.**

- `MigrationChainIntent.keysetUpdateForfeited?: boolean` (T3). When true, the
  planner still EMITS the `define-keyset` step but with `executable: false` and
  a forfeit-specific reason, so the engine's existing non-executable branch
  (`engine.ts:794-802`) reports it and the chain continues — which is exactly
  criterion 8's "forfeit proceeds with every other step and is reported, not an
  error", with no new engine path.
- It is **not** written to `MigrationProgress`. A persisted forfeit is a
  decision that silently outlives the session that made it, and the codec's
  top-level allowlist (`codex-core/src/codex/codec.ts:197`) would have to grow
  for a flag whose whole lifetime is one button press. The section holds it in
  component state, per press, lifted out of T5's gate.
- The engine's refusal is the BACKSTOP, not the only gate: T5's panel computes
  satisfiability before the press, so the normal path is press-once-and-run.
  Criterion 5 is still satisfied literally — a press with an unsatisfied keyset
  and no forfeit returns `"refused"` and submits nothing.
