# migration-execute — the on-chain transaction chain — Plan

Execution plan for `docs/work/migration-execute/design.md`. The design calls this
"assembly, not new capability", and that is true of the TRANSACTIONS. It is not
true of the CALLABILITY: today not one leaf operation can be invoked without
mounting a React modal and a human pressing Execute. So the plan is three waves —
make every leaf callable headlessly, then build the engine over them, then wire
the single press.

## Before you start

### The method is not optional

1. **TDD, strictly.** For every task: write the failing test FIRST, run it, and
   WATCH it go RED *for the reason you intended* — not for a typo, a bad import,

#### (2) The cross-chain flow is EXTRACTED, not re-implemented

The design asks and does not answer. The answer is extract, for three reasons:

- **Consolidation needs it up to nine times** (chains 1-9 → chain 0), and the
  flow is ~110 lines with four distinct failure modes, one of which
  (`"pending"`, `SendStoaModal.tsx:460-472`) is deliberately worded to avoid
  inviting a duplicate resubmit. Nine re-implementations of that judgement is
  nine chances to get it wrong with money.
- **This codebase already rejected the duplicate once, for this exact flow.**
  `pollStoaChainConfirmation` was made public rather than copied precisely
  because "duplicating this fetch/retry/timeout logic a second time would be
  exactly the 'two independently-editable copies that can silently disagree'
  trap this package's own conventions warn against" —
  `zbom/toast/toastManager.ts:287-295`.
- **The engine only ever needs the non-chain-0 branch.** Consolidation's source
  chain is 1-9 by construction, so the engine always takes
  `SendStoaModal.tsx:439-447`'s path (`buildCTransferAcross` → `sign` →
  `submitCrossChainTransfer`), which already goes through `getFailoverClient`
  and therefore already has the retry safety decision (3) demands. The chain-0
  initiate branch (`:409-437`, which goes through `execute()`) stays a modal
  concern and is supplied to the extracted function as an **injected
  `submitInitiate`** callback. That keeps `buildGasStationTransaction` — and
  therefore the only `.setMeta(` in the file — inside `SendStoaModal.tsx`,
  which matters for the test lock described below.

The extracted function returns a **discriminated result**, never throws for a
flow outcome: `{ ok: true, requestKey, continuationRequestKey }` or
`{ ok: false, kind: "invalid-receiver" | "initiate-failed" | "initiate-pending"
| "spv-timeout", message }`. The modal maps those to its existing strings; the
engine maps them to HALT. Both get the same facts.

#### (3) Submit pipeline: `getFailoverClient`, everywhere, no exceptions in the engine

`CodexSigningStrategy.execute()`'s own doc comment settles this. Read it at
`node_modules/@stoachain/stoa-core/dist/signing/codexStrategy.js:39-56`:

> *"Unlike `getFailoverClient.submit` (which captures the same signed-tx
> reference across primary+fallback attempts to preserve mempool dedup), this
> seam deliberately runs without failover (REQ-04) and therefore has **NO
> built-in dedup safety on retry**. … Better: use `getFailoverClient` directly
> for non-codex submit flows so the dedup contract handles this for you."*

The engine is, by design decision §4, a thing the user **re-presses**. A pipeline
with no dedup on retry is the wrong pipeline for it: a `TIMEOUT` on submit may
already have reached chainweb, a re-press rebuilds with a fresh `creationTime`,
and both land. For a transfer that is paying twice.

**The rule: every operation the engine invokes submits through
`getFailoverClient`.** Seven of the eight already do (see the hazard section's
file/line list). The single exception is **B**, the same-chain drain, which today
only exists inside `execute()` — so T7 gives it a self-contained
`getFailoverClient` implementation in the `rotatePaymentKeyLive.ts` style
(`dirtyRead` → calibrate → `universalSignTransaction` → `submit`,
`rotatePaymentKeyLive.ts:120-146`).

`CodexSigningStrategy.execute()` stays exactly where it is today — in the
modals, driven by a human who can see the result and decide. It is never on the
engine's path. Say that in `engine.ts`'s header.

#### (4) Confirmation: only `"success"` unblocks. `"failure"` AND `"pending"` both HALT.

`pollStoaChainConfirmation` (`zbom/toast/toastManager.ts:297-351`) polls 40 × 5s
≈ 200s and then, at `:350`, does
`ctrl.updateStep(stepIdx, 'done', { label: 'Submitted', requestKey })`. It
returns `Promise<void>`. So from a caller's side a timed-out step and a
confirmed step are **indistinguishable** — both end in `status: 'done'`
(`:333` vs `:350`), and neither is reported back. **It is a DISPLAY function. It
must never be the engine's gate.**

The engine's gate is `pollTransactionStatus` from
`@ouronet/ouronet-core/interactions/crossChainFunctions` — chain-generic despite
the file name (`crossChainFunctions.js:202-233`: it just does
`getFailoverClient(chainId).pollOne({ requestKey, chainId, networkId })`) and
already verdict-returning (`"success" | "failure" | "pending"`). Wrapped in a
bounded retry it is exactly `SendStoaModal.tsx:176-188`'s private
`waitForInitiateConfirmation`, whose own doc comment states the discipline:

> *"Exhausting the budget returns `"pending"` — distinct from `"failure"` — so
> the caller never reports a merely-slow confirmation as a hard failure (which
> would invite a duplicate resubmit of a transfer that may still land)."*

**The rule:**

- `"success"` → mark the step `done`, run the next step.
- `"failure"` → mark the step `error`, **HALT the chain**.
- `"pending"` (budget exhausted, outcome genuinely unknown) → mark the step
  `done` with the label **"Submitted — not confirmed"**, **HALT the chain**, and
  say in the toast that re-pressing will re-read the chain.

Why `pending` halts, stated for the case that makes it load-bearing — C→D.
C (`coin.C_URV|Unstake`) moves urSTOA from the vault to liquid. D transfers
**liquid** urSTOA. If the engine treated C's `pending` as a green light it would
read D's amount from a balance that does not yet reflect C, and one of two things
happens: D transfers a stale amount and fails on chain, or C lands after D and
the unstaked funds sit liquid on the OLD key while the toast reads "done". Both
are funds stranded on a key the account no longer names. Halting costs the user
one more button press; guessing costs them their money. The same rule makes
decision §4's idempotence do the work: the next press re-reads chain state, so a
late-landing transaction is simply observed, never replayed.

Note this is not a hot path — StoaChain's polling cadence comment
(`toastManager.ts:353-359`) calls its finality "near-instant", so `pending` is
the pathological case, not the common one.
